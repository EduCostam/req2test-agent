# Suposições e limites da Fase 1

- Correção após validação local do usuário: as imagens foram construídas, mas migrate recebeu ECONNREFUSED. O health check original sem host podia aceitar o servidor temporário via socket Unix. Agora exige TCP em 127.0.0.1:5432 antes de liberar migrate. A nova execução Docker ainda deve ser confirmada pelo usuário; nenhum volume precisa ser apagado.

- **Docker não foi verificado por mim (agente).** Por instrução do usuário, não executei Docker nesta fase. Dockerfile, Compose, health checks e integração PostgreSQL real devem ser validados localmente pelos comandos do README. Testes de SQL com mock não provam funcionamento do banco.
- Ambiente de implementação: Node 24.16.0. `engines.node` exige >=20; `.nvmrc` e imagem Docker usam 24. Node 20 não foi executado neste ambiente. pnpm fixado em 10.28.0; a instalação inicialmente tentou o pnpm 11 do ambiente, depois foi refeita com 10.28.0.
- Provider padrão: FakeLLMClient, sem rede, chave ou gasto real. O adaptador HTTPS compatível com chat completions foi testado com transporte injetado, não com provedor real. Cada provedor pode ter diferenças de protocolo.
- Falhas iniciais: SHA-256 de `seed:question`, primeiro inteiro big-endian módulo 100 menor que 15. Seed 10 foi escolhida para exercitar exatamente 3/20 reparos no corpus smoke; seed 42 havia produzido 1/20. Isso configura injeção de falhas, não demonstra qualidade. Outras amostras/seeds podem variar. Repetir a mesma pergunta repete o comportamento; reparos válidos por padrão. Scripts explícitos permitem erros permanentes e timeouts nos testes.
- `confidence` é um campo validado, não probabilidade calibrada. Fake devolve conteúdo fixo e tokens estimados por caracteres/4. Preços fictícios estão identificados; `is_simulated` é persistido em toda chamada.
- Sem RAG, `sources` deve estar vazio; fontes inventadas ou tool calls são rejeitadas. A qualidade factual não é verificada nesta fase.
- Limites: 32 KiB por body, 8.000 caracteres por pergunta, 2.048 tokens solicitados por geração, no máximo três chamadas (original + dois reparos), timeout individual configurável. Não há retry de rede nesta fase.
- SSE emite `status` seguido de `result` ou `error`; não transmite tokens. Erros após os headers usam evento `error` com HTTP 200. `stream?` é apenas contrato futuro. Se o consumidor desconectar durante a chamada, ela pode terminar e ser contabilizada, limitada pelo timeout; cancelamento propagado do HTTP fica para evolução posterior.
- Histórico, perguntas, respostas e chaves não são persistidos nesta fase. Guardamos metadados operacionais; logs usam campos permitidos e excluem conteúdo pessoal. Runs podem permanecer `running` após queda abrupta; checkpoints/retomada pertencem à Fase 3.
- Chamadas sem resposta do provedor têm tokens e custo NULL (desconhecidos), nunca zero presumido. Falha de persistência não produz resposta de sucesso. Uma interrupção do banco depois da chamada pode deixar registro `running`; reconciliação durável pertence às fases seguintes.
- Compose usa credenciais de desenvolvimento e portas vinculadas a localhost. Auth e controles de produção são Fase 4. Não publicar esta API diretamente na internet.
- As lições cobrem apenas os conceitos implementados. Filas, autenticação, RAG, ferramentas, judges e deploy serão documentados nas fases correspondentes. Não há pacote tools vazio para inflar cobertura.
- CI completo é Fase 5. Nesta fase os checks são comandos reproduzíveis locais e relatórios versionados; não afirmamos CI verde no GitHub.
